# Bun 1.4.2 Upgrade Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move the repo's Bun toolchain pin from 1.4.0 to 1.4.2, correct the stale 1.3.14 pin in the Cursor bootstrap, and adopt `--prefer-offline` on every cached CI install.

**Architecture:** Bun's version is pinned in five independent places that must agree: `.bun-version` (read by `oven-sh/setup-bun` in all three workflows), `package.json` (`engines.bun` + `packageManager`), the two `Dockerfile` build stages, `.cursor/install.sh`, and the `CONTRIBUTING.md` prose. This plan changes them together, then applies one orthogonal CI improvement (`--prefer-offline`) that Bun 1.4.1 introduced. No product code changes.

**Tech Stack:** Bun 1.4.2, Turborepo, Changesets, Docker (`oven/bun` alpine images), GitHub Actions.

## Global Constraints

- Target Bun version is exactly `1.4.2`. The floor in `engines.bun` is `>=1.4.2`.
- **Do NOT delete `packages/cli/scripts/resign-standalone-binary.ts`, its `TODO(oven-sh/bun#39764)` comment, its call in `build-binary.ts`, or the `runs-on: macos-latest` release job.** Upstream fixed the darwin-**arm64** signature in 1.4.1, but `bun-darwin-x64` compile output *still* fails `codesign -v` on 1.4.2 (verified by direct measurement — see Task 3). The release publishes both darwin arches, so the resign path remains load-bearing.
- `--prefer-offline` only. Never `--offline`: it hard-fails on a cache miss, and the CI cache key is `hashFiles('bun.lock')`, so any lockfile change is a guaranteed miss.
- The changeset must target the product package `aio-proxy`, not only internal packages, or its GitHub Release note is silently dropped (see `CLAUDE.md` → Changesets).
- `bun.lock` will be rewritten by `bun install` on 1.4.2 (workspace versions resync from a stale `0.12.3` to the current `0.18.0`). Commit that churn in Task 1; do not revert it.
- Two test failures are **pre-existing on 1.4.0 and out of scope** — do not fix them, and do not treat them as upgrade regressions:
  1. `@aio-proxy/plugin-openai-chatgpt#test:artifact` — `oauth.smoke.ts` reads `./dist/plugin.js`, but rslib emits `dist/plugin/plugin.js`. Broken since commit `5843b66e` moved `src/plugin.ts` into `src/plugin/`.
  2. `bun run lint:types` — 8 `TS2307` errors under `website/` because the patched `@rspress/core@2.0.19` extracts only a partial `dist/` tree with no `package.json`. Reproduced identically under Bun 1.4.0 and 1.4.2, and with the patch removed the package extracts fully — so it is the patch interacting with the isolated linker, not a Bun version regression.

### Task 4: Adopt `--prefer-offline` on cached CI installs

**Files:**
- Modify: `.github/workflows/ci.yml:28`
- Modify: `.github/workflows/release.yml:55`
- Modify: `.github/workflows/deploy-website.yml:35`

**Interfaces:**
- Consumes: the Bun 1.4.2 pin from Task 1. `--prefer-offline` was added in Bun 1.4.1, so these edits are invalid until `.bun-version` is bumped.
- Produces: nothing other tasks depend on.

Bun 1.4.1 added `--prefer-offline`, which skips revalidating cached-but-expired registry manifests while still downloading anything genuinely absent. All three workflows already restore `~/.bun/install/cache` keyed on `hashFiles('bun.lock')`, so the revalidation round-trips are pure waste on a cache hit.

Measured locally (1248 packages, warm cache, `rm -rf node_modules` before each run):

| command | wall clock |
|---|---|
| `bun install --frozen-lockfile` | 8.88s |
| `bun install --frozen-lockfile --prefer-offline` | 7.40s |
| `bun install --frozen-lockfile --offline` | 7.25s |

`--prefer-offline` captures nearly all of the benefit while still tolerating a cache miss. **Do not use `--offline`** — it fails outright when a package is uncached, which is exactly what happens whenever `bun.lock` changes and invalidates the cache key.

`Dockerfile:24` is deliberately excluded: its `bun install --frozen-lockfile` runs in a fresh image layer with no warm `~/.bun/install/cache`, so `--prefer-offline` would buy nothing there.

- [ ] **Step 1: Update the CI workflow install**

In `.github/workflows/ci.yml`, change line 28 from:

to:

      # so skip revalidating cached manifests. Not --offline, which hard-fails on a
      # cache miss (guaranteed whenever bun.lock changes the cache key).
      - run: bun install --frozen-lockfile --prefer-offline

## Out of Scope

Investigated and deliberately excluded. Recorded so they are not re-litigated.

**`--bytecode` on the compiled binary.** Built and measured both variants:

| | size | cold start (`plugin list`, median of 5) |
|---|---|---|
| current | 75.10 MB | 0.17s |
| `--bytecode` | 75.54 MB | 0.17s |

Larger, no faster. The binary is dominated by the ~61.9 MB Bun runtime plus ~4.1 MB dashboard assets and ~1.7 MB agent artifacts; there is too little JS for bytecode to pay off, unlike the Claude Code case in Bun's release notes.

**`bun test --parallel` / `--isolate`.** Bun 1.4.1 fixed `--isolate` memory leaks, but on `@aio-proxy/server`, `--parallel` measured *slower* (31.35s vs 28.05s serial) **and failed one test** — a config-reload fixture parsed `providers` as `undefined`, indicating shared state across files. Adopting it requires isolating that fixture first; that is its own change.

**Bundler flags (`--min-chunk-size`, `--no-split-require`, module preloading).** The dashboard builds with rsbuild/rspack, not `bun build`. `bun build` is used only on the `--compile` path in `build-binary.ts`, where these flags do not apply.

**`Bun.write()` streaming for the CLI self-upgrade.** `packages/cli/src/upgrade/binary.ts:120` buffers the tarball via `res.arrayBuffer()`, which looks like a fit — but the next line hands those bytes to `Bun.Archive` to extract `package/bin/aio-proxy`, so the complete buffer is required anyway. Streaming to disk would add a round-trip.

**Removing `canonicalizeLoopbackHost`.** Bun 1.4.1 resolves `localhost` internally for `fetch`/`WebSocket`/`Bun.connect`, but `packages/core/src/network/canonicalize-loopback-host.ts` validates whether a *bind address* is loopback (for CSRF origin and control-plane locality checks) rather than dialing anything. The runtime change does not cover it. Noted because it is easy to mistake for newly-redundant code.

**The two pre-existing failures** (`openai-chatgpt` artifact test, `website` `TS2307` errors). Both reproduce on Bun 1.4.0 and are unrelated to the upgrade. Fixing them inside a toolchain bump would obscure whether the bump was clean.

**Bumping the `@types/bun` catalog entry to `^1.4.1`.** Tried and reverted. The catalog pins `^1.3.14`, and npm's latest `@types/bun` is `1.4.1` (there is no `1.4.2`). Bumping it resolves and installs cleanly and all `@aio-proxy/core` tests pass, but `bun run lint:types` goes from 8 errors to 13: the newer types break Hono's `ClientResponse` assignability to `Response` at five dashboard call sites —

- `packages/dashboard/src/modules/providers/services/provider-options-schema-service.ts:49` and `:67`
- `packages/dashboard/src/modules/providers/services/oauth-service.ts:60`
- `packages/dashboard/src/modules/agent-authorizations/services/agent-authorizations-service/agent-authorizations-service.ts:28` and `:40`

each `TS2345: Argument of type 'ClientResponse<…>' is not assignable to parameter of type 'Response'`. That is a real typing fix, not a version bump, so it belongs in its own change. Note the existing `^1.3.14` range already *resolves* to 1.4.1 for a fresh install — only `bun.lock` holds it at 1.3.14 — so the repo is one unrelated `bun update` away from meeting these errors regardless.
